# 🤖 Computer Use Automation — Technical Report

## 1. Project Overview

**Computer Use Automation** is an AI-powered browser automation system designed to allow an LLM agent to plan and execute browser actions using Playwright.

The system combines:

* **Groq LLM** for task planning
* **Playwright** for browser interaction
* **FastAPI** for backend APIs
* **Safety policies** for controlled actions
* **Capability Artifacts** for reusable automation workflows
* **Deterministic Replay** for executing previously validated workflows
* **Human-in-the-Loop** intervention for sensitive or uncertain situations

The overall objective is to create a controlled computer-use agent that can convert natural-language instructions into safe, executable browser actions.

# 3. Core Components

## 3.1 AI Planner

The planner receives the user's goal and browser observation and generates the next action.

Example:

```json
{
  "type": "click",
  "locator": {
    "role": "button",
    "name": "Submit"
  },
  "value": null
}
```

The planner should be responsible for:

* Understanding the user's goal
* Selecting the next action
* Producing structured output
* Identifying task completion
* Requesting escalation when necessary

# 4. Canonical Action Model

One of the major architectural requirements is to use a single action vocabulary across the planner, agent, safety layer, and executor.

The canonical format is:

```json
{
  "type": "click",
  "locator": {},
  "value": null
}
```

Supported action types:

```text
navigate
click
fill
select
press
wait
extract
```

Example:

### Navigate

```json
{
  "type": "navigate",
  "locator": null,
  "value": "https://example.com"
}
```

### Click

```json
{
  "type": "click",
  "locator": {
    "role": "button",
    "name": "Login"
  },
  "value": null
}
```

### Fill

```json
{
  "type": "fill",
  "locator": {
    "label": "Email"
  },
  "value": "user@example.com"
}
```

### Press

```json
{
  "type": "press",
  "locator": {
    "role": "textbox"
  },
  "value": "Enter"
}
```

This common schema prevents mismatches between different layers of the application.

# 5. Safety Layer

The safety layer ensures that the AI agent does not blindly execute every action generated by the LLM.

The system should validate:

* URLs
* Action types
* Allowed domains
* Sensitive operations
* User-provided inputs
* Extracted data

Example safe action list:

```text
click
fill
navigate
wait
select
press
extract
```

The system also includes an allowlist mechanism for controlling which domains the agent can access.

# 6. Critical Issues Identified

During the project audit, several integration problems were identified.

## 6.1 Missing `demo_app_domain`

`AllowlistManager` expects:

```python
settings.demo_app_domain
```

but the settings configuration does not define this property.

This can cause initialization failures.

### Recommended solution

Derive the hostname from the configured demo application URL:

```python
from urllib.parse import urlparse

@property
def demo_app_domain(self):
    return urlparse(self.demo_app_url).hostname
```

This avoids maintaining the same information in two different configuration fields.

# 7. Replay Engine Issues

The replay system had inconsistent interfaces between:

```text
ReplayEngine
ReplayExecutor
ActionExecutor
```

The recommended design is:

```text
ReplayEngine
     │
     ▼
ReplayExecutor
     │
     ▼
ActionExecutor
     │
     ▼
Playwright
```

## Recommended `ReplayExecutor`

```python
class ReplayExecutor:

    def __init__(self, session):
        self.session = session
        self.executor = ActionExecutor(session)
```

The replay executor should convert stored artifact actions into the canonical action dictionary before sending them to `ActionExecutor`.

# 8. Replay Flow

The intended replay flow is:

```text
Capability Artifact
        │
        ▼
ReplayEngine
        │
        ▼
Load Actions
        │
        ▼
ReplayExecutor
        │
        ▼
Canonical Action
        │
        ▼
ActionExecutor
        │
        ▼
Playwright
        │
        ▼
Checkpoint Verification
        │
        ▼
Output Extraction
```

The engine should also properly close its browser/session resources.

Recommended route pattern:

```python
engine = ReplayEngine(artifact)

try:
    result = await engine.replay(inputs)
    return result
finally:
    await engine.close()
```

# 9. Agent Integration

The agent should receive a `PlannerResult` from the planner.

The result should be checked before executing an action.

Possible planner outcomes:

```text
action
goal_complete
escalate
```

The agent should not directly execute a planner-specific object.

Instead:

```text
PlannerAction
      │
      ▼
Canonical Action
      │
      ▼
Safety Validation
      │
      ▼
ActionExecutor
```

This keeps the planner independent from browser execution.

# 10. Artifact Validation

The artifact route requires a consistent validation mechanism.

The recommended approach is to validate incoming artifacts using Pydantic:

```python
artifact = CapabilityArtifact.model_validate(request.artifact)
```

The validated artifact can then be passed to the repository and artifact validator.

This provides a clear boundary between:

```text
API Request
     ↓
Pydantic Validation
     ↓
Artifact Validation
     ↓
Repository
```

# 11. Human-in-the-Loop

The project includes an intervention mechanism for situations where the AI agent should hand control to a human.

Expected flow:

```text
AI Agent
   │
   ├── Safe / deterministic action
   │
   └── Requires intervention
             │
             ▼
       Human Control
             │
             ▼
       Human completes task
             │
             ▼
       Agent resumes
```

The intervention manager should use the agent's handoff interface:

```python
agent.handoff.start_human_control()
```

and:

```python
await agent.handoff.resume_agent(note=note)
```

This keeps human handoff logic inside the agent lifecycle.

# 18. Artifact Versioning

Capability artifacts are intended to represent reusable automation workflows.

A typical artifact can contain:

```text
Artifact
├── metadata
├── actions
├── checkpoint
├── inputs
└── outputs
```

Example:

```json
{
  "name": "login_workflow",
  "actions": [
    {
      "type": "navigate",
      "value": "https://example.com"
    },
    {
      "type": "fill",
      "locator": {
        "label": "Email"
      },
      "value": "{{email}}"
    },
    {
      "type": "click",
      "locator": {
        "role": "button",
        "name": "Login"
      }
    }
  ]
}
```

The artifact can then be replayed without requiring the LLM to regenerate every action.

# 19. Deterministic Replay vs AI Planning

The system separates two important execution modes.

## AI Planning

```text
Goal
 ↓
LLM
 ↓
Action
 ↓
Browser
 ↓
Observation
 ↓
LLM
```

This provides flexibility but introduces LLM variability.

## Deterministic Replay

```text
Stored Artifact
 ↓
Known Actions
 ↓
Browser
 ↓
Checkpoint
 ↓
Output
```

This provides a more predictable execution path for workflows that have already been validated.

# 20. Browser Automation

Playwright is responsible for browser-level execution.

The executor should handle:

```text
Navigation
Clicking
Form filling
Dropdown selection
Keyboard actions
Waiting
Data extraction
```

The executor should not contain LLM reasoning.

Its responsibility should remain:

> Convert validated canonical actions into deterministic browser operations.

# 21. Error Handling

The application should distinguish between different failure categories.

### Planner Error

```text
LLM unavailable
Invalid planner response
Malformed action
```

### Safety Error

```text
Blocked domain
Unsafe action
Invalid locator
Restricted operation
```

### Browser Error

```text
Element not found
Navigation failure
Timeout
Page unavailable
```

### Replay Error

```text
Checkpoint mismatch
Artifact invalid
Unexpected page state
```

This makes debugging and observability significantly easier.

# 24. Security Considerations

Because this project allows an AI system to interact with external applications, security should be treated as a first-class component.

Important controls include:

* Domain allowlisting
* Action validation
* Input sanitization
* Secret protection
* Sensitive-data redaction
* Human escalation
* Browser isolation
* Execution logging
* Checkpoint verification

API keys and credentials must never be hard-coded into source files.

The primary architectural requirement is to maintain a clean separation between:

```text
Reasoning
    ↓
Planning
    ↓
Safety
    ↓
Execution
    ↓
Observation
    ↓
Replay / Verification
```

The identified issues are primarily integration and consistency problems rather than a need to redesign the entire system.

Once the action model, replay interfaces, artifact validation, human handoff, and test configuration are aligned, the project will have a much cleaner foundation for extending the automation agent with additional browser capabilities, stronger safety controls, observability, and production deployment.
